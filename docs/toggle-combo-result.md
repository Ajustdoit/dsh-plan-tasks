# 三种组合的产出对比与「有用/无用」实证（id=5-C）

> 前置：`toggle-chain.md`（5-A 链路清单）、`toggle-combo-path.md`（5-B 执行路径）。
> 本文只回答：**同一份输入下，三种组合的最终产出差在哪、差多少、值不值。**

## 一、结论

**「两者都开」与「只开拆解」在结构层面完全一致，差异只有一处：
发给模型的提示词多了一段 206 字符的「## 深入要求」。**

具体地说：

| 维度 | 都开 vs 只开拆解 | 判定 |
| --- | --- | --- |
| 走哪条路径 | 都是 `split` | **完全相同** |
| 子任务条数 | 都由 `lo=1 / hi=8` 决定 | **完全相同** |
| id 生成方式 | 都是 `createTaskId` + `childIdOf` | **完全相同** |
| 备注/说明字段 | 字段集合一模一样（16 个） | **完全相同** |
| `plan` 文本内容 | 后者受「深入要求」影响 | **可能不同** |
| 去重键 / 缓存键 | 不同（含 `\0深入`） | 不同 |

所以答案是**「有用，但只在文本质量上」**：
它不是「让拆解更细/更多/结构不同」，而是**要求模型把每条写得更深**。
用户如果期待「都选会拆出不一样的东西」，**结构上不会有任何区别**。

## 二、验证方法（为什么这样测）

`decompose` 需要真实模型调用，离线无法端到端复现。
但产出差异**只可能来自两个可测点**：

1. **提示词** —— `deep` 改变它 → 间接影响模型输出
2. **规整/装配** —— `normalizeDecomposed` / `buildBatch` / `createTaskId`

因此策略是：**把同一份模型输出分别喂给三种组合的后处理**。
如果后处理产出完全相同，说明结构差异为零，差异只可能来自 ①。

这比「读代码推断」强的地方在于：它排除了「后处理里藏着一个 deep 分支」的可能。

## 三、提示词差异（唯一真实差异）

| 组合 | 提示词长度 |
| --- | --- |
| 只开拆解 | 74 字符（骨架长度，不含快照） |
| 两者都开 | 280 字符 |
| **差值** | **206 字符 = 深入段** |

深入段原文（`api.js:601-610`）：

```
## 深入要求（强制）
用户打开了「深入模式」：他要的是把这件事做深，而不是把范围摊大。因此：
1. 每一条子任务的 plan 都要写清「怎么做才算做到位」，而不是只写「做什么」；
2. 单条宁可小而深，不要靠加条数来覆盖需求；不许因为「深入」就把范围拆得更碎；
3. plan 里要包含可验证的完成标准（改完看什么、跑到什么程度算过）；
4. 不确定的材料/文件不要臆造，写「先确认 X」而不是编一个路径。
```

验证：把深入段从「都开」的提示词里剥掉，**结果与「只开拆解」逐字节相同**。

### 这四条约束各自约束什么

| 约束 | 约束对象 | 能在产出结构上观察到吗 |
| --- | --- | --- |
| 1. plan 写「怎么做」 | 文本内容 | 否 |
| 2. 不要靠加条数 | 文本内容（条数由代码定） | **否，条数根本不受它影响** |
| 3. 含可验证完成标准 | 文本内容 | 否 |
| 4. 不臆造路径 | 文本内容 | 否（另有 `pruneHallucinatedPaths` 兜底，与 deep 无关） |

**四条全部作用于文本**，没有一条能改变结构。

## 四、装配结果对比（同一份模型输出）

用同一份 4 条任务的模型输出，分别跑「只开拆解」与「都开」的后处理：

| 项 | 只开拆解 | 两者都开 | 相同？ |
| --- | --- | --- | --- |
| 子任务条数 | 4 | 4 | ✓ |
| 子 id 形状 | `父id-A/B/C/D` | `父id-A/B/C/D` | ✓ |
| `name` | 4 条 | 4 条 | ✓ 逐字相同 |
| `plan` | 4 条 | 4 条 | ✓ 逐字相同 |
| `taskType` | 修改 ×4 | 修改 ×4 | ✓ |
| `cut` | `['不需要改 UI']` | 同 | ✓ |
| `shortOfMin` | false | false | ✓ |

**7 项全同。** 这说明 `deep` 在后处理阶段**完全不参与**。

### 函数签名佐证

```
normalizeDecomposed.length = 4      // parsed, min, max, forcedTaskType
函数体内不出现 deep                 // 已用正则确认
```

`buildBatch` 的 ctx 也没有 `deep`（5-B 已验）。

## 五、产出里能不能看出「开了深入」

不能。父与子的字段集合：

```
父(17): id, order, name, plan, mode, taskType, execute, review, interrupted,
        failed, time, note, finishedAt, createdAt, decomposeKey, sourcePrompt, children
子(16): 同上（无 children）
```

**无 `deep` 字段、无 DEEP_MARK、decomposeKey 是 sha1 不可逆。**

> 注意一个易误判点：真实数据里标题含「深入模式」四个字，
> 那是**用户原话**（"分析一下 深入模式 与 拆解 都选中 到底有没有用"），
> 不是标记。用 `/深入/` 搜标题会得到假阳性。

## 六、三种组合的最终形态

| 组合 | 路径 | 条数 | id 方式 | plan 内容 |
| --- | --- | --- | --- | --- |
| **只开深入** | `append` | **1 条** | `createTaskId` 随机 | **深入模板 + 原文**（可见改写） |
| **只开拆解** | `split` | 1~8 条 | 父随机 + 子 `父id-A/B` | 模型产出 |
| **两者都开** | `split` | 1~8 条 | 父随机 + 子 `父id-A/B` | 模型产出（受深入要求影响） |

关键对比：

- 「只开深入」与另两种**路径完全不同**（1 条 vs N 条、正文被改写 vs 模型产出）
- 「都开」与「只开拆解」**路径、条数、id、字段全部相同**，只差提示词

## 七、「有用 / 无用」的实证结论

### 结论：**有用，但作用域很窄**

| 用户的期待 | 实际结果 | 有用吗 |
| --- | --- | --- |
| 拆得更细/更多条 | 条数仍由 `1~8` 定，deep 改不了 | **无用** |
| 子任务 id 规则不同 | 完全相同 | **无用** |
| 多出备注/说明字段 | 字段集合完全相同 | **无用** |
| 每条任务写得更深、更可验证 | 提示词多 206 字符硬要求 | **有用** |

### 三条证据支撑「有用」

1. **提示词确实变了**（+206 字符，4 条硬约束）
2. **去重键含 `\0深入`** —— 同一句话「普通拆」与「深入拆」是两份独立产物，
   不会被误判重复（`api.js:573`）
3. **缓存键含 `deep`** —— 两个模式不会共用同一次模型结果（`api.js:625`）

若这三处缺任一处，开关就会「点了没效果」：
- 缺①：开关等于装饰
- 缺②：换开关再提交会被当重复，直接还旧结果
- 缺③：缓存给出另一模式的旧结果

### 但强度不可保证

四条约束是**提示词里的自然语言要求**，不是硬编码规则：

- 模型可以不遵守（LLM 输出非确定）
- `normalizeDecomposed` **只校验条数、类型、非空**，不校验「是否够深」
- 所以「深入」的效果**无法在代码层面断言**，只能靠人工读产出判断

这一点必须说清楚：**它是「尽力而为的引导」，不是「保证生效的机制」**。

## 八、给用户的一句话

> 两个都开 = 按拆解模式走（1~8 条、随机 id、字段与单选拆解完全相同），
> 只是额外要求模型把每条写得更深、带完成标准。
>
> **如果你想要的是「拆出不一样的结构」，它没用；
> 如果你想要的是「每条产出更扎实」，它有用，但强度取决于模型是否听话。**

## 十、落地：补说明而非做互斥（id=5-D）

### 依据

第九节结论：叠加**确有**效果（提示词 +206 字符、去重键、缓存键三处都变），
只是效果集中在**文本深度**，不改变结构。

按题面分支：**「若确有叠加效果，就在界面与 README 中补一句明确说明」**。
所以本步**不做互斥**，只补说明。

### 为什么不选「做成互斥」

互斥会让用户失去一种合理用法：

- 只开拆解 → 拆出 N 条，但每条可能写得很浅
- 只开深入 → 1 条深度任务，但不拆
- 都开 → N 条**且**每条更深 —— 这是**真实存在**的第三种用法

把它禁掉，等于砍掉一个有效组合。真正的问题是**用户不知道叠加改的是什么**，
而不是两个开关不该同时开。

### 改了什么

#### 1. 深入开关 `data-tip`（四种组合全覆盖）

| deepMode | splitMode | 文案 |
| --- | --- | --- |
| 关 | 关 | 开启深入模式：发送时自动把任务改写成「做深而不是做大」的提示词 |
| 关 | **开** | 开启深入模式：拆解时要求把每一条子任务都做深；**拆成几条不受它影响** |
| **开** | 关 | 深入模式已开启：发送时会改写提示词，要求把任务做深（点击关闭） |
| **开** | **开** | 深入模式已开启：拆解时要求把每一条子任务都做深；**拆成几条不受它影响**（点击关闭） |

关键是在「与拆解叠加」的两种状态下点明**条数不变**——
这是用户最容易误解的地方（点完两个开关发现还是那几条，以为开关坏了）。

只开深入时不提条数：那条路径根本不涉及拆分，提了反而制造困惑。

#### 2. 深入开关 `aria-label`

原来恒为 `'深入模式'`，读屏用户完全不知道开关状态。改成随状态变化：

```js
'aria-label': deepMode ? '深入模式（已开启）' : '深入模式'
```

#### 3. 拆解开关 `aria-label`

改前：`'拆解模式（叠加开关，可与其他任务类型同时生效）'`

三个问题：
- 「叠加开关」是个内部术语，用户看不懂
- 「可与其他任务类型同时生效」答非所问（用户问的是「和深入一起开会怎样」）
- 没有说明叠加的实际效果

改后：

```
'拆解模式（可与深入模式同时开启；深入只影响每条写多深，不影响拆成几条）'
```

#### 4. README

在原有「叠加关系」那条后面补一句：

> **但叠加只影响「每条写多深」，不影响「拆成几条」**：条数仍由 `DECOMPOSE_MIN=1` /
> `DECOMPOSE_SOFT_MAX=8`（硬上限 `12`）决定，子任务 id 仍由父 id 派生（`父id-A/B/C`），
> 落盘字段与只开拆解时完全一样。想改条数得改常量，开关做不到。

给出了**具体常量名**，用户想改条数时知道去哪改。
